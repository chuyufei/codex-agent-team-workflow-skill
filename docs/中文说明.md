# Codex 多 Agent 协作流程 Skill 中文说明

这份文档用于快速了解 `codex-agent-team-workflow` 的定位、使用方式和能力边界。

## 它解决什么问题

这个 Skill 不是让多个 Agent 做角色扮演，而是把复杂项目拆成可追踪、可交接、可验证的协作流程。

它主要解决这些问题：

- 一个长线程里同时做规划、实现、检查，容易混乱。
- 不同任务边界不清，比如数据事实、设计判断、代码实现、发布决策混在一起。
- 多个 Codex 线程之间缺少标准交接格式，后续难以追责和复盘。
- 项目长期迭代时，只靠聊天记录很难沉淀稳定流程。

## 先拆机制，再建团队

收到用户需求后，第一步不是直接套用某个 profile，而是先拆解协作机制并请用户确认：

- 这个任务是否值得多 Agent 协作，还是单线程更直接。
- 需要拆开的责任边界是什么，例如需求、设计、数据、代码、验证、文档、发布。
- 每个 Agent 的输入、输出、允许路径、禁止路径和验收标准是什么。
- 使用 `generic`、`web-static`、`content-team`，还是为当前项目定制更小的组合。

profile 是起点模板，不是约束。SaaS、数据分析、GitHub PR、内容发布等场景都应按真实任务边界设计协作机制。

## 默认最小团队

不确定怎么拆时，从三 Agent 起步：

- Manager agent：负责方向、范围、任务 brief 和验收标准。
- Executor agent：按 brief 产出实现或交付物，不自行扩大范围。
- Validator agent：按验收标准独立检查，不同时承担实现工作。

当项目确实需要更细边界时，再增加 design、data、assets、release、docs、research 等 Agent。

## 关键文件

- `skills/codex-agent-team-workflow/SKILL.md`：Skill 本体，定义什么时候触发、怎么执行。
- `skills/codex-agent-team-workflow/agents/openai.yaml`：Codex UI 展示元数据。
- `skills/codex-agent-team-workflow/references/workflow-guide.md`：团队拓扑和工作流设计参考。
- `skills/codex-agent-team-workflow/references/templates.md`：Agent 注册表、handoff、worklog 等模板参考。
- `skills/codex-agent-team-workflow/references/principles.md`：核心协作原则。
- `skills/codex-agent-team-workflow/scripts/bootstrap_agent_docs.py`：在目标项目里生成协作文件的脚本。
- `docs/USAGE.md`：使用流程。
- `docs/EXAMPLE_PROJECT_SETUP.md`：项目落地示例。

## 怎么使用

安装到本地 Codex skills 目录：

```powershell
Copy-Item -Recurse .\skills\codex-agent-team-workflow "$env:USERPROFILE\.codex\skills\codex-agent-team-workflow"
```

重启 Codex 后，可以这样调用：

```text
Use $codex-agent-team-workflow to set up a multi-agent workflow for this project.
```

也可以直接用脚本给某个项目生成协作文件：

```powershell
python .\skills\codex-agent-team-workflow\scripts\bootstrap_agent_docs.py "<project-path>" --profile generic
```

生成中文模板：

```powershell
python .\skills\codex-agent-team-workflow\scripts\bootstrap_agent_docs.py "<project-path>" --profile generic --language zh
```

可选 profile：

- `generic`：manager、executor、validator 三 Agent 最小配置。
- `web-static`：适合静态站、前端项目、设计预览和数据展示项目。
- `content-team`：适合内容运营、选题、素材、审核类流程。

脚本默认不会覆盖已有文件，除非显式加 `--force`。

## 适合使用的场景

- 项目涉及产品、设计、数据、代码、测试、文档、发布等多个边界。
- 需要独立验证，而不是让实现者自己验收自己。
- 项目会长期迭代，需要留下 durable docs 和工作日志。
- 需要把多个 Codex 线程当成长期 Agent 使用。
- 需要标准 handoff，避免多线程之间信息丢失。

## 不适合使用的场景

- 只是一个小修小补。
- 只是解释一段代码或回答一个问题。
- 一个命令或一个文件改动就能完成。
- 当前 Codex 环境没有线程管理工具，而用户也不想手动复制 handoff 消息。

这类场景直接用单线程完成更简单。

## 能力边界

这个 Skill 定义的是协作流程和模板，不承诺所有 Codex 环境都支持创建、读取、改名或发送消息到其他线程。

如果当前环境有线程管理工具，就用工具创建和管理 Agent 线程。

如果没有，就仍然使用 `AGENT_REGISTRY.md`、handoff 模板和 worklog 模板，但由用户手动把消息复制到对应线程。

## 发布前检查

发布或打包前，人工确认不要包含本机绝对路径、私有 thread ID、token/API key、临时目录、缓存目录，以及不适合公开发布的内部来源描述。
